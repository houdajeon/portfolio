CRUD Master

Une plateforme de films découpée en trois microservices Python sur trois VM Vagrant : une API gateway, une API d'inventaire en HTTP et une API de facturation alimentée par RabbitMQ.

Le backend d'une petite plateforme de streaming de films, construit en microservices. Une API gateway est le point d'entrée unique : elle transmet les requêtes /api/movies à l'API d'inventaire en HTTP, et publie les commandes de facturation dans une file RabbitMQ que l'API de facturation consomme. Les deux API sont écrites en Python avec Flask, chacune avec sa propre base PostgreSQL, et chaque service tourne dans sa propre machine virtuelle créée par Vagrant.

Le problème

GET {{gateway}}/features

Fonctionnalités

  • API d'inventaire : un CRUD REST sur /api/movies et /api/movies/<id> (GET, POST, PUT, DELETE), avec recherche par titre
  • API de facturation : lit les commandes JSON de billing_queue, les enregistre dans la table orders, puis acquitte chaque message
  • API gateway : transmet /api/movies à l'API d'inventaire en HTTP et publie POST /api/billing dans RabbitMQ
  • Trois VM lancées avec un seul vagrant up : gateway-vm, inventory-vm et billing-vm
  • Tous les identifiants dans un seul fichier .env, transmis aux services par Vagrant, aucun écrit dans le code
  • Services gérés avec PM2, tests Postman pour chaque endpoint, et un fichier OpenAPI pour la gateway

POST {{gateway}}/api/billing

Défis techniques

  • Aucune commande perdue quand la facturation est arrêtée

    en file
    La gateway doit accepter les commandes même quand l'API de facturation est arrêtée, et elles doivent être enregistrées dès son retour.
    ack
    La gateway se contente de publier la commande dans RabbitMQ et répond tout de suite. Les commandes attendent dans billing_queue, et l'API de facturation n'acquitte un message qu'une fois enregistré : tout ce qui est en attente est traité à son redémarrage. Nous l'avons testé avec pm2 stop et pm2 start. [TODO: confirmer, et ajouter comment la file survit à un redémarrage de RabbitMQ, par exemple des files durables]

  • Deux façons de communiquer

    en file
    L'inventaire a besoin d'une réponse immédiate, alors que la facturation peut se faire un peu plus tard.
    ack
    HTTP pour l'API d'inventaire, dont la gateway renvoie la réponse telle quelle, et une file de messages pour la facturation : la gateway n'attend jamais le traitement d'un paiement.

  • Une seule configuration pour trois machines

    en file
    Les noms de bases, utilisateurs, mots de passe et URL sont nécessaires sur trois VM différentes.
    ack
    Un seul fichier .env lu par le Vagrantfile, qui transmet les valeurs à chaque VM et à chaque service, et des scripts d'installation dans scripts/ qui installent les outils et créent les bases.
